# 多节点像素图标注任务启动 Prompt

复制下文作为新节点的启动消息。每个节点填写不同的 `NODE_INDEX`，所有节点使用相同的 `NODE_COUNT` 和服务端地址。编号从 0 开始。

---

请启动并持续执行 pixel art / 拼豆图纠错标注任务，目标是把分配给本节点的样本逐张标注好，积累可用于训练的纠错数据。

## 本节点配置

```text
项目目录：<本节点的 pixelization_native 项目路径>
PIXEL_ANNOTATION_SERVER：<所有节点共用的服务端 URL>
NODE_INDEX：<本节点编号，从 0 开始>
NODE_COUNT：<参与节点总数>
尺寸：24、52、78、104，全部处理
```

认证令牌和 Python 路径使用环境中已有的 `PIXEL_ANNOTATION_TOKEN`、`PYTHON`；不要输出令牌。远程节点必须填写管理节点可访问的 URL，不能把自己的 localhost 当成管理节点。

## 先了解现有实现

进入项目，阅读适用的 AGENTS.md、`docs/annotation-client.md`，以及 CLI 的帮助和相关实现：

- `packages/pixel-annotate/pixel_annotate.ts`
- `scripts/pixel_annotation_recipes.py`
- 服务端共享配方 `scripts/annotation_profiles/<原图编号>.json`

以当前代码和服务端状态为准。检查连接和必要依赖即可；现有 Web 功能已经人工验证，不要启动一轮无关的应用测试、重构、重新生成预测图或重启管理服务。

## 多节点分工：按原图编号分片

样本例如 `4236_52`，其中原图编号为 4236，尺寸为 52。

**仅处理满足 `原图编号 % NODE_COUNT == NODE_INDEX` 的样本。**

同一原图的四种尺寸归同一个节点，因为四种尺寸共用一份配方。不要只按尺寸拆给不同节点，也不要修改其他分片的共享配方。运行期间不要自行改变节点总数或分片规则。

当前 `next` 不会领取或锁定任务，不能把返回一个 ID 当成独占授权。先筛选自己的分片。遇到 409 冲突，重新读取最新状态与资源，检查是否有人已经修改；不能用强制覆盖来绕过冲突。

## 优先级与状态

1. 优先处理本分片的 `unqualified`，读取每张图片的审核原因及必要的历史记录，逐条解决。
2. 再处理本分片的 `unmodified`。
3. 跳过 `pending`、`human_edited`、`qualified`，不要主动覆盖人工修改或待审核结果。
4. AI 的修改统一提交为 **`pending`（待审核）**。最终合格与不合格由用户决定，不能自行批量判为合格。
5. `--force` 仅用于刚刚重新核实仍为 `unqualified` 的确切样本和尺寸，不得用于整个队列。

使用分页查询队列，按数值原图编号整理本分片任务。不要仅靠搜索 ID 前缀来确定分片。队列中的审核原因可能不完整，应读取 `resources/indices/<样本ID>` 中的 `review_reason`、`review_history` 等当前字段。

队列会随提交而缩短：不要一边修改队列一边递增 offset，造成漏项。可以先读取候选 ID 快照，再逐条重新核实；完成一批后重新读取队列。

## 每张图的操作闭环

1. 读取原图、预测图、现有纠错图、调色板、当前状态和审核原因。
2. **实际打开图片观察**，对照原图判断主体、姿态、轮廓、色块和关键细节。不能只读文件名或数值指标就提交。
3. 选择适合这张图的处理方式：已有配方、局部像素修改、区域改色、轮廓重画或指定尺寸手工像素稿。
4. 生成本次修改涉及尺寸的预览，打开并逐张检查。发现问题继续修；配方或处理代码有变化后必须重新生成并查看预览。
5. 提交前重新核实目标样本状态和最新内容，避免覆盖用户或其他节点的新修改。
6. 通过 CLI 提交为 pending，确认服务端保存成功，保留 corrected、edit_mask、metadata，以及原始 prediction。
7. 继续下一张。遇到难图可以迭代重画，不能用批量套参数、自动通过或长期跳过来代替标注。

## 视觉质量要求

- 逻辑像素编辑、固定调色板索引、透明像素为 -1，预览使用最近邻。
- 画面应由有意义、连贯的色块组成。消除杂色、彩边、白边、孤立碎点、断线和意外透明孔洞。
- 保留主体的轮廓、姿态、比例和辨识特征；特别检查眼睛、瞳孔、高光、嘴巴、鼻子、手脚、文字和细长部件。
- 24 像素版要单独设计与检查，必要时简化细节；不要直接缩小较大尺寸就提交。52、78、104 也需分别检查。
- 区分真实白色物体与外围白边，保护眼白、牙齿、手套、衣领、标志等。
- 清理轮廓时，有些像素应改成相邻轮廓色，有些应删除；不能统一删除浅色，也不能把所有边缘都涂黑。
- 多角色或复杂场景必要时按角色、区域分别描画。整体加粗轮廓或统一降色可能破坏形状，必须看实际效果。
- 不追求一个算法自动解决所有图，最终依据逐图视觉检查决定是否可以送审。

## 使用并积累 CLI 能力

优先使用已有命令，先查看当前帮助确认参数。常用命令包括：

```sh
node packages/pixel-annotate/pixel_annotate.ts list --status unqualified --limit 100 --offset 0
node packages/pixel-annotate/pixel_annotate.ts show 4236_52
node packages/pixel-annotate/pixel_annotate.ts palette
node packages/pixel-annotate/pixel_annotate.ts recipe-preview 4236 --sizes 24,52,78,104
node packages/pixel-annotate/pixel_annotate.ts recipe-apply 4236 --sizes 24,52,78,104
```

上面的编号只是命令示例，不是额外分配给你的任务。只对自己的分片执行实际修改。按具体状态和修改范围传入 `--sizes`，不要无意覆盖其余尺寸。

已有工具包括：

- `profile-tune`、`profile-threshold`、`profile-color`：覆盖率与颜色映射。
- `profile-patch`、`profile-region`、`profile-stroke`、`profile-ellipse`：局部色块与轮廓细节。
- `profile-grid`：保存指定尺寸的手工像素稿。
- `profile-clean-fringe`：清理边点；可用 `--to` 改色、`--rect` 限定区域、`--keep` 保护区域。
- `profile-fill-holes`：按区域、颜色和像素数上限填补封闭透明孔洞。
- `profile-label`、`profile-rays`、`profile-mirror`、`profile-fit`：文字、放射线、镜像与布局调整。
- `edit`、`save`：单样本精细像素编辑与提交。
- `export`：按需导出 PNG，默认到执行节点的 Downloads。

重要细节：

- `profile-set` 会重建整份配方，不得用来随意覆盖已有手工稿。
- 已有某尺寸的 `grid` 时，该尺寸直接使用手工稿，其他区域、笔画等参数不会作用于它；需要编辑该 grid。
- 很多配方命令使用 512 基准坐标；`edit`、`profile-grid`、`profile-label` 等使用逻辑像素坐标。逐条确认，不要混用。
- `--ink` 与覆盖率 class 参数可能指原图颜色类别位置，而非最终调色板索引；阅读帮助和实现后使用。
- 不要猜色板索引，查询服务端权威调色板。
- 把重复操作归纳为参数化命令或可复用配方，避免每张图都写一套临时脚本。确需增强公共 CLI 时，保留已有行为，记录用法；多节点使用相同代码版本，不擅自推送、部署或覆盖其他节点代码。

## 数据与协作边界

所有权威数据通过服务端 HTTP API 读取和写入。不要直接操作服务端 SQLite、复制数据库或把本地文件当成权威样本状态。临时预览和计算可以在本节点运行。

共享配方通过 CLI/API 保存，归管理节点 Git 工作区管理，不要把 annotation_profiles 加入 gitignore。保留他人已有修改；没有明确要求不要提交 Git commit。

不使用图像生成服务代替逻辑像素标注。使用项目现有 CLI 和 Python 图像处理能力，输出可追溯的像素稿、修正图和编辑 mask。

## 持续执行与汇报

配置明确后直接开始，不要反复询问是否继续。执行期间简短汇报正在处理的编号、具体问题与修复方式。

每批记录本节点实际成功提交的样本 ID、修改内容、待处理难点和新增的可复用命令。提交待审核不等于用户已经确认合格，不要宣称整个数据集完成。

只有重新查询确认本分片没有待处理的未修改或驳回样本后，才能汇报“本节点当前分片已处理完，剩余待人工审核”。遇到连接或依赖问题先排查，并准确报告实际阻塞原因。
